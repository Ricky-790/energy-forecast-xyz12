## Assistant

Not safely as written. `sync_runs` is not really a sync log; it is the cache coverage index. Removing it and checking only for row presence changes behavior in two important ways.

**1. Missing data vs. never fetched**

If Elexon returns no rows for a window, SQLite stays empty for that window. Without `sync_runs`, the next request sees “no rows” and assumes it is a cache miss, so it calls Elexon again. The early-January 48h-lead gaps would be re-fetched on every request. Same for any date where actuals have not been published yet.

**2. Forecast presence does not mean the cache is complete**

Forecast rows are publications, not one row per target interval. A target can have a cached publication while publications closer to the requested cutoff were never fetched.

Example:

- Request Jan 1-2 fetches publications through Jan 2.
- Elexon returns forecasts for Jan 5 from those publications, so Jan 5 has rows in SQLite.
- Later request Jan 5 with a 24h lead only checks “does Jan 5 have a forecast row?” and skips fetching.
- But publications from Jan 3-4 were never fetched. The app would select the old Jan 2 publication, possibly a 72h lead, instead of the latest publication before the 24h cutoff.

`sync_runs` is what tells the backend that publication coverage stopped at Jan 2, so it fetches the missing publication window. Without it, “row exists” is not enough to guarantee the selected forecast is correct.

**Other required changes if removed**

- Remove `SyncRun` from `db_schemas.py`, `_coverage`, `_record_run`, and the `SyncRun` queries in `elexon.py`.
- Remove or null `last_sync_at` in `DataStatusResponse` and `main.py`; nothing in the frontend uses it.
- Rewrite `ensure_data` to detect missing target hours/dates and fetch their publication/date windows. This is presence-based, not coverage-based.
- Update the README caching description.
- Existing databases would keep the old `sync_runs` table unless it is explicitly dropped; `create_all` will not remove it.

**Recommendation**

If the goal is to eliminate sync-run history, keep a minimal coverage table — just `dataset`, `range_type`, `range_start`, and `range_end`, dropping `row_count` and `synced_at`. That is a cache index, not a sync log, and preserves the current correctness and lazy-fetch behavior.

If you want no extra table at all, we can do presence-based gap detection, but we would be accepting repeated Elexon calls for genuinely missing windows and the forecast-cutoff staleness risk above. That is a behavior change, not a no-op refactor.

Do you want the minimal coverage table, or the fully table-free presence-based behavior?

Yes — that is the piece that makes removing `sync_runs` viable. But the key should not be `(lead, publication)` alone.

**Correct key**

Use:

```text
(dataset, target_start_time, requested_lead_hours)
```

and store:

```text
publish_time
generation_mw
status = ok | missing
```

The publication time is a value, not part of the key. There should be one selected forecast per target and requested lead.

**Why not `(lead, publication)`**

Elexon does not return lead time. It returns `startTime` and `publishTime`, and we derive lead as `startTime - publishTime`.

A requested lead is a cutoff, not an exact publication time. For Jan 5 12:00 at 24h, the cutoff is Jan 4 12:00. If Elexon’s latest publication is Jan 4 11:30, that is the selected forecast, with an actual lead of 24.5h. Keying by exact 24h would miss it. Keying by `(target, requested_lead)` stores the row that was actually selected.

**How the cache works**

For a missing target block `[B0, B1)`:

1. Fetch publications from `B0 - 72h` to `B1`.
2. For every target in that block and every supported lead, compute the cutoff and select the latest publication at or before it.
3. Write one row per target/lead: `ok` with the selected publication, or `missing` if no publication qualifies.
4. Only write a row when the fetch covered that lead’s cutoff. The window above covers all supported leads for the block.

Then a request checks the selection rows for its target range and lead. If every row exists, including `missing` rows, no Elexon call is needed. If rows are absent, those target blocks have never been fetched, so fetch only those blocks.

This solves the Jan 5 stale-publication problem from the earlier example: the first Jan 1-2 fetch would not store a Jan 5 24h row because it did not cover the Jan 4 cutoff. The later Jan 5 request would see the row is absent and fetch the needed publication window.

**What changes**

- The `forecasts` table changes from raw publications to selected forecasts keyed by `(start_time, requested_lead_hours)`.
- `sync_runs`, `_coverage`, `_record_run`, and `last_sync_at` are removed.
- `select_forecasts` becomes a direct lookup of the cached selection.
- `ensure_data` checks selection rows and fetches contiguous missing target blocks.
- Switching between lead times does not refetch, because one publication fetch can populate all supported leads.
- The cache database must be reset or given a new table because the forecast schema changes.

For actuals, we can use date-level presence: if a settlement date has any actual rows, treat it as cached; otherwise fetch that date. A genuinely empty date would be retried, but January actuals are complete. If you want exact empty-date caching, that needs a missing marker, which is a small coverage mechanism.

So the answer is yes: with a `(target_start_time, requested_lead_hours)` selection cache, `sync_runs` can go and the lazy-cache behavior stays correct. Do you want to go with that design?

## Design decisions

- **UTC everywhere**, clearly labelled.

## Gist of `elexon.py`

It's the **Elexon sync + caching layer**: everything that talks to the upstream Elexon API and writes the results into SQLite. It has five logical parts:

**Types & shared state**
- `ElexonError` — the single error type callers catch (raised as HTTP 502 in `utils.ensure_request_data`).
- `SyncStats` — a Pydantic counter/accumulator (`fetched_from_elexon`, row counts, `windows`) with `extend()` to merge forecast + actual syncs.
- `_sync_lock` — an `asyncio.Lock` that serialises all syncs so concurrent requests don't double-fetch.

**HTTP fetch**
- `_request_json` — one dataset chunk, 3 retries with backoff, retries on 429/5xx, fails fast on 4xx.
- `_fetch_forecasts` — pulls `WINDFOR` for a publication window (chunked, concurrent), dedups on `(start_time, publish_time)`.
- `_fetch_actuals` — pulls national `FUELHH` `WIND` for a date range, dedups per `start_time` keeping the latest publication.

**Cache-gap detection**
- `_forecast_targets_missing` — asks `forecasts_service.coverage` which `(target, lead)` pairs exist, then returns targets missing any required lead.
- `_time_blocks` / `_date_blocks` — collapse sorted hours/dates into contiguous blocks so each upstream call covers a maximal range.

**Selection & write**
- `_build_forecast_selections` — for each target hour it applies the cutoff rule (`publish ≤ target − lead`) per `CACHED_LEAD_TIMES` and emits one `ok`/`missing` row per lead.
- `_sync_forecasts` / `_sync_actuals` — detect gaps, fetch, and hand rows to `forecasts_service.upsert_selections` / `actuals_service.upsert`.

**Orchestration**
- `data_window` — turns a request range into a target start plus inclusive actual settlement dates.
- `ensure_data` — the public entry point: under the lock, sync forecasts then actuals, returning merged `SyncStats`.

## Accuracy screen (`AccuracyScreen.tsx`, built by `analysis.build_accuracy`)
`ok` means **the hour has both a usable forecast and an actual at the same instant**:
- the forecast for that `start_time` at the selected lead is valid (a publication existed at/before the cutoff), **and**
- an actual exists at that exact `start_time`.

Only these rows produce an error and feed `mae_mw`, `rmse_mw`, `bias_mw`, and the tolerance calc (`analysis.py:190-198`). The neighboring badges are the failure cases:
- `missing_forecast` → "No forecast" (actual present, forecast absent)
- `missing_actual` → "No actual" (forecast present, actual absent)
- `missing_both` → "No data"

Matching is **exact `start_time` equality only**. A `:30` actual can never match an hourly forecast row, so it never shows "Matched" — it's counted separately as `unmatched_actual_count`.

## Forecast screen (`ForecastScreen.tsx`, built by `analysis.select_forecasts`)
`ok` means **only that a forecast publication was found for that hour at the requested lead** — i.e. a publication whose publish time is at or before `start_time − lead`. There's no actual involved here at all.

`missing` → "Missing" means no publication at or before the cutoff (either no cached row for that lead, or the cached row isn't `ok`); the row shows the reason "No publication at or before the cutoff" (`ForecastScreen.tsx:73-74, 397-399`).

## The catch
The word "Matched" is overloaded. On the **Accuracy** screen it means "forecast and actual matched to each other." On the **Forecast** screen it means "matched to a valid forecast publication at the cutoff," not matched to an actual. If that's confusing, the fix is a labeling change in `STATUS_LABELS` (or per-screen labels), not a logic change — say the word and I can plan that.

## Assistant

Quick correction on the premise: it's the **other way round**.

- **Forecasts** (`WINDFOR`) are **hourly** — one value per hour, on the `:00`.
- **Actuals** (`FUELHH`, national WIND) are **half-hourly** — one value per settlement period, on `:00` *and* `:30`.

So the mismatch is "hourly forecast vs half-hourly actual," and the backend's answer is: **it doesn't reconcile them at all — no interpolation, no averaging.** It matches on exact `start_time` and simply drops the `:30` actuals, while exposing them so the exclusion is visible.

## How the gap is handled

1. **Forecasts are pinned to a whole-hour grid.** Everything iterates `hourly_intervals`, so one forecast row per hour:
   - grid generator: `utils.hourly_intervals` (`utils.py:60-67`)
   - one selection per hour per lead: `elexon._build_forecast_selections` (`elexon.py:235-279`, the `for target in hourly_intervals(...)`)
   - API output one row per hour: `analysis.select_forecasts` (`analysis.py:47-97`)

2. **Actuals are loaded as-is** (including `:30`), keyed by `start_time`, into a dict — `analysis.load_actuals` (`analysis.py:100-119`). It picks the latest publication per timestamp; it does **not** coarsen half-hours to hours.

3. **Matching is exact-timestamp lookup, not interpolation** — `analysis.build_accuracy` (`analysis.py:179-198`):
   ```python
   actual = actuals.get(forecast.start_time)   # exact match only
   ...
   error = forecast.forecast_mw - actual.generation_mw
   ```
   A forecast at `14:00` looks up the actual at exactly `14:00`. The `14:30` actual is never referenced, so it can't contribute to MAE/RMSE/bias.

4. **The dropped `:30` actuals are counted and surfaced** — `analysis.py:222-224`:
   ```python
   unmatched_actual_count = sum(
       1 for start_time in actuals if start_time.minute != 0
   )
   ```
   That number is returned as `metrics.unmatched_actual_count`, shown in the review screen's "Method" note (`AccuracyScreen.tsx`, "Forecasts are hourly. Actuals are half-hourly. Only exact start-time matches are compared, so …").

5. **The tolerance endpoint uses the identical exact-match rule** — `analysis.compute_tolerance` (`analysis.py:136-143`), same `actuals.get(item.start_time)` lookup, so it's scored on the same sample set.

## Bottom line
There is no "making up." The effective comparison set is the hourly forecast grid, and each hour is scored against the actual at that same hour. Half-hour (`:30`) actuals are stored but excluded from every metric, and `unmatched_actual_count` reports how many were excluded so it isn't silent.

If you'd *want* them reconciled (e.g. average the two half-hours into an hourly actual, or compare the forecast to both `:00`/`:30` points), that's a real design change in `build_accuracy` + `load_actuals` + `compute_tolerance` — say so and I'll plan it (I'm in Plan mode, so no edits yet).
